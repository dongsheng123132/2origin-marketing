<h2>一个只在「别人打开它」的时候才存在的 bug</h2>

<p>我们的基准论文里有一句底气很足的话：数据和判分器全部公开，<strong>表里每一格都能从原始数据重新算一遍</strong>。§7 给了仓库地址。</p>

<p>问题是，读者点开那个地址，落地在默认分支 <code>main</code> 上。而 <code>main</code> 上：</p>

<ul>
  <li>没有 <code>results-v3-m/</code>——主表那 60 个 per-round 原始 JSON，一个都不在</li>
  <li>没有判分器变异测试</li>
  <li>没有 textbook 方言</li>
  <li><code>paper</code> 目录里只剩 v0.1 和一份旧的 v0.2</li>
</ul>

<p>东西都在，只是都在另一个分支上。<strong>我们最强的那个卖点，在唯一一个外人会打开的地方，恰恰是验不了的。</strong></p>

<h2>为什么这类问题特别难被自己发现</h2>

<p>因为开发的人永远站在 feature 分支上看，那里什么都齐全。跑得通、数字对、命令有效——每一次自查都是绿的。</p>

<p>这是「在我这儿是好的」的升级版本：<strong>在我这儿是「公开」的。</strong></p>

<p>它跟一句空话之间只差一个视角：<strong>「我们写了」和「外面的人能验」是两件事。</strong>前者由我们决定，后者由 <code>git clone</code> 之后的第一眼决定。</p>

<h2>修法：把 29 个提交并回主干</h2>

<p>处理办法不是往 README 里加一句「请切到 xx 分支」，那是把自己的疏漏转嫁给读者。办法是把该公开的东西合并到默认分支：<strong>29 个提交，0 冲突</strong>（数字取自该次合并的提交说明）。</p>

<p>顺带上主干的还有：上下文编译器 v0.2（相机 + 三档 LOD + 预算斜坡）、帧与差分、video / textbook / paper 三个方言、判分器变异测试，以及论文 v0.3 的送审前自查。</p>

<p>还有一张表也一起上去了——概念体系的<strong>实现状态列</strong>，上面五个部件明写着 <code>candidate：零实现、零判据</code>。合并主干等于把「我们还没做的东西」也一并公开了。这是刻意的：<strong>只把好看的合上主干，就又变成了另一种「在我这儿是公开的」。</strong></p>

<h2>顺便说说变异测试，它比「测试通过」值钱</h2>

<p>「我的测试全绿」证明不了多少事——测试可能压根没盯着关键那段逻辑。变异测试反过来问：<strong>我故意把判分器改坏，你的自测能发现吗？</strong></p>

<p>我们往判分器里注入了 9 个 bug，每一个都是真出过或差点出的那种：</p>

<ul>
  <li>准确率恒为满分</li>
  <li>召回率的分母用「找到的」而不是「种下的」</li>
  <li>漏报的字段不再算错</li>
  <li><code>not_contains</code> 判反</li>
  <li>严格比对退化成字符串比对</li>
</ul>

<p><strong>9 个全部被杀死，0 个存活。</strong>这句话的意思是：如果哪天有人（包括我们自己）把判分器改松了，自测会当场变红。</p>

<h2>我们不宣称的部分</h2>

<p>按规矩把边界写清楚：</p>

<ul>
  <li>ShadowBench-W 目前仍是 <strong>v0.1 草案</strong>，不是已定稿的标准</li>
  <li>那五个 <code>candidate</code> 部件<strong>确实还是零实现、零判据</strong>，上了主干不代表做出来了</li>
  <li>这次合并还漏下一个未推送的提交（法律方言的回归修复），是另一个会话在做的活，留给它自己推——<strong>写在提交说明里，不藏</strong></li>
</ul>

<p>最后一条大概是这件事真正的收获：<strong>让外人能验，是一个需要专门去做的动作，不是写完代码自动获得的属性。</strong></p>

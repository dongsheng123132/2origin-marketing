<h2>一句话，先于代码存在</h2>

<p>2026-08-08，一次关于协议边界的讨论里冒出这么一段判断。原话，未加工：</p>

<blockquote>
<p>MCP 的 elicitation 只覆盖「这一次调用要不要问人」。你要的是更上一层：授权凭据在层间可继承——南桥算出的 risk 和它接受的凭据，要能沿 Harness → Adapter → 南桥 这条链传递并被上游理解。</p>
<p>一句话：不是南桥的责任，是 Harness Adapter 的责任；Adapter 之上那层可继承的授权凭据，才是 2Origin 该发明的东西。</p>
</blockquote>

<p>这篇记的不是一个功能，是这句话怎么成形的。它此刻没有实现、没有落地，唯一跑起来的只有一个原型。</p>

<h2>第一件事不是庆祝，是 grep 自己</h2>

<p>兴奋的当口最容易犯的错，是把新名字当成新发现。所以第一步是查重。</p>

<p>结果：<strong>「本源总线 OriginBus」根本不是今天的新词。</strong>它从 RFC-0000 第一天就在架构表里，原文是：</p>

<pre><code>| 高速总线 | 北桥 | **OriginBus** | 把相关状态编译进 Context |</code></pre>

<p>它还是 TRADEMARKS.md 里登记在册的商标词。这篇要是写成「今天发现了一个叫本源总线的新东西」，读者点开 RFC-0000 一眼就能拆穿。</p>

<p>连「OriginBus Trust 层」这个说法都不新——RFC-0000 早就写着「跨 harness 真正缺的不是状态格式，而是 OriginBus Trust 层的统一写授权」。那今天新在哪？</p>

<h2>新的是归属，不是名字</h2>

<p>RFC-0000 原文的下一句是：「这是『南桥』/ Trust Plane 的职责，本架构将其列为必建组件。」英文版走得更远，直接给这条证据标了 <code>SOLVED ✅</code>——南桥 MCP server 提供白名单加审计的写通道，Codex 调用成功，25 字节落盘。</p>

<p>今天改的就是这一句。<strong>责任从南桥改派给 Harness Adapter，并提出 Adapter 之上要有一层「可继承」的授权凭据。</strong>新的是「凭据沿 Harness → Adapter → 南桥 这条链继承、并被上游理解」这个机制，不是 OriginBus 这个词。</p>

<p>名字是旧的，归属是新的——这个区分是全文最要紧的一句。</p>

<h2>改派的依据：一行不存在的日志</h2>

<p>推翻自己的结论要的是证据，不是新想法。这次的证据是一行日志——准确说，是<strong>没有</strong>那行日志。</p>

<p>南桥的 MCP server 注册成功、握手成功，工具清单里也有它。但每次调用都返回 <code>user cancelled MCP tool call</code>，而南桥自己的 <code>audit.log</code> <strong>一条记录都没有</strong>。</p>

<p>零记录是铁证：请求从未到达南桥。南桥那套分级授权——风险三级、乐观锁、人在环确认——完全正确，却<strong>一次也没机会执行</strong>。它不是判错了，是压根没被问到。</p>

<p>病根随之清楚：</p>

<pre><code>Harness 审批闸门   ← 有【决策权】，没有【判断依据】
      ↓ tools/call     ✗ 请求死在这里
南桥               ← 有【判断依据】，没有【决策权】</code></pre>

<p>让被拦在门外的一方去解决「我为什么被拦」，是无解的。这就是把 Trust 责任压在南桥头上的错——南桥永远在门的另一侧。</p>

<p>回头看，那个 <code>SOLVED ✅</code> 也站不住：验证命令带着 <code>--approve-for-me</code>——一次性放开所有工具的全局开关。用「把闸门全关掉」证明「分级授权可行」，自相矛盾。这处文本此刻还没改，我们把它记进债务清单，而不是悄悄改掉当没发生。</p>

<h2>Adapter 才是责任方——而且它已经发生过一次</h2>

<p>「Harness Adapter」在 RFC-0000 里原本只是个接入兼容层，不承担 Trust 职责。改派之后它的定义变成：<strong>把 OriginBus 的授权表达，翻译成目标 harness 的闸门认得的形式。</strong></p>

<p>这不是设想。同一天已经做过一次，只是当时没命名：MCP 通道堵死之后，加了一条不经过该闸门的 CLI 通道，与 MCP 共用同一个动作核心。第三个 harness 经它成功落盘，两条通道判决字节级一致，审计里两条记在 <code>southbridge_cli</code> 名下、<code>southbridge_mcp</code> 零条。</p>

<p>关键是它<strong>没有降低任何授权要求</strong>：风险分级照跑、批准凭据照要、写后观察照做、审计照记。它只是换了一条 harness 本来就信任的路。这跟「把闸门关掉」是两回事。</p>

<h2>为什么是「证明你读过」，不是「你被批准了」</h2>

<p>手上唯一跑起来的原型是 <code>expect_sha256</code>：覆盖一个已存在的文件前，先出示它当前内容的 sha256，对得上才放行。</p>

<p>它和「批准」的区别不是实现细节，是分水岭：</p>

<ul>
<li><strong>「你被批准了」是一个断言。</strong>它需要一个能弹窗、能点确认的人在场。无头 agent——后台任务、定时任务、另一台机器上的 harness——没有人可以问，它永远拿不到这句话。</li>
<li><strong>「证明你读过当前内容」是一个可核验的事实。</strong>无头 agent 读得了文件、算得出哈希，所以它自己就能出示；没读过就想覆盖的 agent，出示不了。</li>
<li><strong>它还会自己过期。</strong>别人在你读完之后改过这个文件，哈希就不匹配，写被拒——同一个凭据顺手解决了静默覆盖。</li>
</ul>

<p>可离线出示、可被第三方复核、会自己过期——这三条是「批准」这种断言给不了的。所以它被当作 Trust 通道的第一个凭据类型，而不是一个乐观锁小功能。</p>

<h2>状态：一个提案，加一个原型</h2>

<p>这一节最容易被误读，所以说死：</p>

<ul>
<li><strong>「凭据可继承」= 提案，没有实现。</strong>Harness 收到凭据、理解它、据此决定放不放行——目前没有任何 harness 支持，我们也没法单方面实现。</li>
<li><strong><code>expect_sha256</code> = 原型，能跑。</strong>但它只覆盖「目标有可读的当前内容」这类动作——启动进程、发消息、调外部 API 出示不了。第二种凭据长什么样，没有实测支撑，不猜。</li>
<li><strong>codex 的 MCP 闸门仍未解。</strong>那是 harness 侧缺少按 server 授信的能力，不是我们单方面能修的。</li>
<li><strong>写这篇稿子时，相关 RFC 草案刚落盘、还没提交。</strong>它给这个概念上了号，但没有给它实现。上号不等于落地。</li>
</ul>

<p>数字也核过一遍。讨论当场引用的测试数是错的；实跑 <code>npm test</code> 是 <strong>38 tests / 38 pass</strong>（当天上午还是 34，新 RFC 落地后变 38）。乐观锁有专项测试覆盖（<code>乐观锁：expect 不匹配则拒绝写</code>），南桥 medium 风险那条测试的批准路径也走它——但 38 是整机的数字，<strong>不能按到单个特性头上</strong>。</p>

<h2>值得在这个时候写下来的原因</h2>

<p>2Origin 在 RFC-0000 §1 声明过：它不定义模型，不替代 MCP、A2A 或任何 Harness，它定义的是「更高一层」的问题。这种话很容易变成空话——直到你能指出一个具体的、别人确实没覆盖的空位。</p>

<p>今天指出了一个：MCP 的 elicitation 覆盖「这一次调用要不要问人」，前提是调用得先到达 server；当 harness 的闸门位于 server 之上、而且只有全局开关时，授权表达如何仍然成立——这一格 MCP 没有，A2A 也没有。</p>

<p>它现在还只是一个提案。但一个能被指出来的空位，比十句「更高一层」有用。而这天真正的收获也许不是那个概念，是查重那一步：<strong>连自己名字里已经有的东西，也要先查一遍再说「新」。</strong></p>
